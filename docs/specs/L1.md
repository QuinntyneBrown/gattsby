# L1 - High-Level Requirements

*Gattsby. Derived from [`docs/application-brief.md`](../application-brief.md) on 25 November 2026.
The detailed requirements, with acceptance criteria, phases, platform dependencies, assumptions and
open questions, are in [`L2.md`](L2.md).*

Gattsby's mission (L0) is not written yet. When it is, it goes in `docs/specs/L0.md`, and every L1
below traces to it.

## L1-001: Environment and capability detection
Gattsby must determine, before and during an investigation, which of the browser capabilities it
depends on are present (Web Bluetooth, the Prompt API and its model, experimental advertisement
scanning, the camera, secure context, storage) and must tell the person plainly what is missing,
what that limits and how to fix it.

## L1-002: Operating modes
Gattsby must run the diagnostic playbook in full agent mode, with an on-device model choosing the
next step, and in checklist mode, without any model, and must route to checklist mode automatically
whenever no model is usable.

## L1-003: Investigation lifecycle
Gattsby must let the person start, follow, pause, stop and finish an investigation of one device,
beginning with preparation (machine type, brand, powering on, freeing the device from other
connections).

## L1-004: Device discovery
Gattsby must find the device the person is standing next to, using the narrowest scan first and
widening it only when needed, and must tell apart several candidate devices.

## L1-005: Connection management
Gattsby must connect to the chosen device, keep the connection, detect and recover from drops, and
release the connection when the investigation ends.

## L1-006: Device identification
Gattsby must identify the device's maker, model, firmware and Bluetooth protocol from its name,
advertised and discovered services, Device Information and the protocol knowledge base, and, as an
option, from a photo of its model plate or console.

## L1-007: Standard protocol verification
Where the device exposes a standard Bluetooth SIG profile, Gattsby must decode its data and confirm,
with live data and a physical action by the person, that the decoded metrics are correct.

## L1-008: Proprietary protocol analysis
Where the device's data is not in a known format, Gattsby must record it, find the fields that vary
with the person's actions, infer their encoding and framing where it can, and report what it could
and could not decode, without attempting to bypass encryption or authentication.

## L1-009: Safe device control
Gattsby must determine which features of the device can be controlled and may confirm one of them
with a single low-risk command, only with the person's explicit approval for each command, and must
offer an emergency stop at all times.

## L1-010: Agent orchestration
Gattsby must run a bounded observe → decide → act loop in which the model chooses one validated
action at a time, deterministic code executes and decodes, and the loop always ends.

## L1-011: Interaction with the person
Gattsby must ask the person questions, ask for physical actions and, as an option, capture photos,
in a way a non-technical helper can follow while standing next to a machine.

## L1-012: Hypotheses, verdict and device profile
Gattsby must track its protocol hypothesis with confidence and evidence, end every investigation with
a verdict, and produce a device profile that another app can consume.

## L1-013: Missing-tool requests
Gattsby must record every capability the agent needed but lacked, with the reason and the evidence,
so that it guides future development.

## L1-014: Persistence, import and export
Gattsby must keep every investigation and its record in the browser, survive interruptions without
corrupting them, and let the person export and import profiles and records as versioned JSON.

## L1-015: Protocol knowledge base
Gattsby must hold its protocol knowledge (service and characteristic UUIDs, standard decoders, vendor
signatures, name patterns, manufacturer IDs, safe command limits) as versioned data that can be
extended without changing code.

## L1-016: Tool registry
Gattsby must describe every tool the agent can use in a typed registry (schemas, safety class,
preconditions) from which the model's tool list is generated, so that tools can be added without
changing the agent loop.

## L1-017: Safety
Gattsby must never move, reconfigure or modify a device without the person's in-the-moment approval,
must keep every command conservative, and must never change a device's settings, pairings or
firmware.

## L1-018: Privacy and security
Gattsby must keep all data on the device, make no network requests at run time beyond its own static
files, and treat model output, device data and imported files as untrusted.

## L1-019: Performance
Gattsby must reach a verdict for a standard FTMS machine within minutes and must respond to each step
quickly enough for a person standing next to the machine.

## L1-020: Reliability and offline operation
Gattsby must work offline once loaded, and must keep working, or fail safely, when a connection, the
model or storage misbehaves.

## L1-021: Usability, accessibility and responsive layout
Gattsby must be usable one-handed, at arm's length, on a phone or a laptop, by a person with or
without technical knowledge, and must meet WCAG 2.2 AA across all viewport sizes.

## L1-022: Maintainability and testability
Gattsby must isolate every browser API behind an adapter, keep its data formats versioned, and be
testable end to end without a real device, Bluetooth radio or model.

## L1-023: Later-phase capabilities
Gattsby must leave room for capabilities beyond the MVP (a model on phones, sharing profiles) without
committing to them before their open questions are answered.
