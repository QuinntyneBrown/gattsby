## Conventions

**IDs.** Every L2 requirement has one unique ID. As the brief asks, the prefix says its kind:
`FR-` (functional), `NFR-` (non-functional) or `TOOL-` (tool specification). These IDs take the
place of the skill's `L2-NNN` numbering; all three kinds are L2 requirements. IDs are never reused
or renumbered.

**Phase.** Each requirement has a **Phase**:

| Phase | Meaning |
|---|---|
| **MVP** | Needed for the MVP. The MVP identifies an FTMS treadmill or bike end to end, in full agent mode and in checklist mode, and meets the brief's six MVP acceptance criteria. |
| **P2** | The next phase: proprietary-protocol depth, vendor signatures, photos, experimental scanning. |
| **Later** | Depends on an open question being answered first. |

**Platform dependency.** A requirement that depends on a browser capability that is experimental,
behind a flag or limited to some platforms carries a **Platform** line naming one or more of these
flags. [Section 5](#5-platform-dependency-register) lists every flagged requirement.

| Flag | Capability | Status (25 November 2026) |
|---|---|---|
| `PD-PROMPT` | Prompt API (`LanguageModel`) with Gemini Nano | Shipped in Chrome 148 for Windows, macOS, Linux and Chromebook Plus only. Not in Chrome for Android or iOS. The model downloads separately on first use and needs significant free disk space. |
| `PD-PROMPT-IMAGE` | Image input to the Prompt API | Listed as a Prompt API feature; availability by platform and model version must be detected, not assumed. |
| `PD-BLE` | Web Bluetooth (`navigator.bluetooth`) | Chrome on desktop and Android only; not on iOS, Safari or Firefox. Secure context only. `requestDevice()` needs a user gesture. |
| `PD-BLE-SERVICES` | Access to GATT services | Only services named in `filters` or `optionalServices` are reachable; Chrome's GATT blocklist hides some UUIDs entirely. |
| `PD-ADV` | `watchAdvertisements()` and `requestLEScan()` | Experimental, behind a flag (Chrome Canary or `chrome://flags`). |
| `PD-GETDEVICES` | `navigator.bluetooth.getDevices()` | Behind a flag on some platforms (new permissions backend). |
| `PD-CAMERA` | Camera through `getUserMedia` | Needs permission; availability varies by device. |
| `PD-WEBGPU` | WebGPU for an in-browser model | Availability and performance vary widely on phones. |
| `PD-STORAGE` | Persistent IndexedDB storage | The browser may evict data unless `navigator.storage.persist()` is granted. |
| `PD-PWA` | Service worker and install | Install prompts and behaviour vary by platform. |

Every requirement that touches a device depends on Web Bluetooth. To keep the flags meaningful, `PD-BLE` is listed only where a requirement turns on Web Bluetooth's limits (platform support, secure context, user gesture, reconnection); every other flag is listed wherever it applies.

**Acceptance test traceability.** Every acceptance test file starts with a header naming the
requirement IDs it covers, for example:

```typescript
// Acceptance Test
// Traces to: FR-024, FR-025, TOOL-013
// Description: Decode FTMS treadmill data and confirm speed rises when the person walks faster
```

**Words.** "The person" is whoever holds the phone or laptop. "The device" is the machine or sensor
being identified. The other terms (investigation, action, tool, safety class, approval, playbook,
full agent mode, checklist mode, observation, hypothesis, verdict, device profile, missing-tool
request, knowledge base) are defined in [`AGENTS.md`](../../AGENTS.md#words).

**Authority.** The brief is authoritative for technical scope. The companion *Gattsby: Behavior
Description* is authoritative for user-facing behaviour (wording, screens, flows) but is not yet in
the repository; every user-facing string quoted below is provisional until it is (see
[OQ-06](#7-open-questions)).

## 1. Functional requirements (FR)

### Environment and modes

## FR-001: Check capabilities on start
**Traces to:** L1-001 · **Phase:** MVP · **Platform:** `PD-BLE`, `PD-PROMPT`, `PD-ADV`, `PD-CAMERA`

When the app opens, and before every investigation, Gattsby must run `check_capabilities`
([TOOL-001](#tool-001-check_capabilities)) and show the result as a short list: Bluetooth, model,
advertisement scanning, camera, storage. Each item is *available*, *needs action* (with the action)
or *not available* (with what that limits).

**Acceptance Criteria:**
1. Given Chrome 148 on macOS with Bluetooth on and the model downloaded, when the person opens
   Gattsby, then every item reads *available* except advertisement scanning, which reads *not
   available* with "Only in Chrome with experimental features turned on".
2. Given Chrome with the computer's Bluetooth turned off, when the person opens Gattsby, then
   Bluetooth reads *needs action* with "Turn on Bluetooth", and the start button is disabled until a
   re-check passes.
3. Given any browser, when the capability check runs, then it completes within 1 second, excluding
   any model download, and raises no uncaught error.

---

## FR-002: Explain an unsupported browser
**Traces to:** L1-001 · **Phase:** MVP · **Platform:** `PD-BLE`

Where Web Bluetooth is absent (Safari, Firefox, any browser on iOS), Gattsby must say that it cannot
reach a device in this browser and name the supported browsers and platforms. It must not offer to
start an investigation.

**Acceptance Criteria:**
1. Given Safari on iOS, when the person opens Gattsby, then the page says the browser cannot use
   Bluetooth, names Chrome on a laptop or on Android, and shows no start button.
2. Given Firefox on Windows, when the person opens Gattsby, then the same message names Chrome on
   Windows, and no call to `navigator.bluetooth` is attempted.
3. Given an unsupported browser, when the person opens the investigation history, then past
   investigations and profiles can still be viewed, imported and exported.

---

## FR-003: Require a secure context
**Traces to:** L1-001 · **Phase:** MVP · **Platform:** `PD-BLE`

Gattsby must detect when it is not running in a secure context (HTTPS or `http://localhost`) and
must say that Bluetooth needs HTTPS.

**Acceptance Criteria:**
1. Given the app served over plain `http` from a host other than localhost, when it opens, then it
   says Bluetooth needs a secure (HTTPS) address and offers no scan.
2. Given the app served over HTTPS, when it opens, then no secure-context message is shown.

---

## FR-004: Report model availability and download progress
**Traces to:** L1-002 · **Phase:** MVP · **Platform:** `PD-PROMPT`

Gattsby must call `LanguageModel.availability()` with the same options it will use to create a
session, and must reflect each state: *available*, *downloadable* (offer the download, warn about
size and disk space), *downloading* (show progress as a percentage), and *unavailable* (say why, and
that checklist mode will be used).

**Acceptance Criteria:**
1. Given availability `downloadable`, when the person opens Gattsby, then it offers "Download the
   on-device model" with a note that it is large and needs free disk space, and does not start the
   download until the person taps it.
2. Given the person has started the download, when the model reports progress, then a progress bar
   shows the percentage, updated at least once a second, and the person can continue in checklist
   mode meanwhile.
3. Given availability `unavailable` (for example on Chrome for Android), when the person opens
   Gattsby, then it says the on-device model is not available on this device and that the
   investigation runs as a checklist.
4. Given the download fails, when the failure is reported, then Gattsby says so, offers a retry, and
   checklist mode stays usable.

---

## FR-005: Choose the operating mode
**Traces to:** L1-002 · **Phase:** MVP · **Platform:** `PD-PROMPT`

At the start of each investigation Gattsby must use full agent mode when a model session can be
created and checklist mode otherwise. The person must be able to choose checklist mode even when a
model is available. The current mode must be visible throughout the investigation and recorded in
the investigation record.

**Acceptance Criteria:**
1. Given a model is available, when the person starts an investigation, then it runs in full agent
   mode and the screen shows "Agent".
2. Given no model is available, when the person starts an investigation, then it runs in checklist
   mode and the screen shows "Checklist", with no model call attempted.
3. Given a model is available and the person chose checklist mode, when the investigation runs, then
   no model call is made.
4. Given any investigation, when it is exported, then its record states the mode for every step.

---

## FR-006: Fall back to checklist mode during an investigation
**Traces to:** L1-002 · **Phase:** MVP · **Platform:** `PD-PROMPT`

If the model fails during an investigation (session creation fails, a call times out twice in a row,
the context is exhausted, or three consecutive actions fail validation), Gattsby must switch to
checklist mode at the current playbook stage without losing observations, and tell the person.

**Acceptance Criteria:**
1. Given full agent mode at the Identify stage, when two consecutive model calls time out, then
   Gattsby switches to checklist mode at Identify, keeps every observation and hypothesis, and shows
   "Continuing as a checklist".
2. Given three consecutive model actions fail validation, when the third fails, then Gattsby switches
   to checklist mode and records the three rejected actions in the investigation record.
3. Given a fallback has happened, when the investigation finishes, then its verdict and profile are
   built the same way as in an investigation that started in checklist mode.
4. Given a model session stops or the compact prompt no longer fits, when the next choice is offered,
   then Gattsby records the reason, stage and triggering step in the investigation record.

---

### Investigation lifecycle

## FR-007: Start an investigation
**Traces to:** L1-003 · **Phase:** MVP

The person must be able to start a new investigation in one tap from the home screen. Gattsby must
create the investigation record at once, with a start time, the mode, the app version and the
knowledge-base version.

**Acceptance Criteria:**
1. Given the capability check passes, when the person taps "Identify a device", then a new
   investigation is created and stored before the first prompt appears.
2. Given an investigation was created, when it is inspected in the store, then it holds its start
   time, mode, app version and knowledge-base version.

---

## FR-008: Prepare the device and the person
**Traces to:** L1-003 · **Phase:** MVP

The Prepare stage must ask the machine type (treadmill, bike, rower, cross-trainer, heart-rate
sensor, other, don't know) and the brand (free text with suggestions from the knowledge base, or
"don't know"); ask the person to power the device on; and ask them to disconnect the console's own
app, watches, phones and any other app that may hold a Bluetooth connection to the device.

**Acceptance Criteria:**
1. Given a new investigation, when Prepare runs, then the person is asked the machine type and the
   brand, each with "Don't know" as an answer.
2. Given the person answered, when Prepare continues, then Gattsby asks them to power the device on
   and to disconnect other apps and watches, and waits for "Done".
3. Given the person answered "Don't know" to both questions, when Prepare ends, then the
   investigation continues to Find without treating the unknowns as errors.

---

## FR-009: Stop, pause and resume an investigation
**Traces to:** L1-003 · **Phase:** MVP

The person must be able to stop an investigation at any time. Stopping halts the agent loop, sends
no further command, disconnects and records the verdict *Stopped by the person* with what was
learned so far. An investigation interrupted by closing the tab or a crash must be resumable from
its last completed step, with a reconnect.

**Acceptance Criteria:**
1. Given an investigation in progress, when the person taps "Stop", then no further tool runs, the
   device is disconnected within 2 seconds, and the investigation is stored with verdict *Stopped by
   the person*.
2. Given the tab was closed during the Identify stage, when the person reopens Gattsby, then it
   offers to resume that investigation, and resuming starts with a reconnect.
3. Given a stopped investigation, when the person opens it from the history, then its observations,
   hypothesis and partial profile are shown.

---

## FR-010: Label the location
**Traces to:** L1-003 · **Phase:** MVP

The person may type an optional location label (for example, a store name). Gattsby must never
determine location on its own. The label can be up to 120 characters after trimming whitespace.

**Acceptance Criteria:**
1. Given an investigation, when the person types a location label, then it is stored in the
   investigation and copied into the device profile.
2. Given any investigation, when it runs, then the Geolocation API is never called.

---

### Discovery

## FR-011: Scan with known-UUID filters first
**Traces to:** L1-004 · **Phase:** MVP · **Platform:** `PD-BLE`, `PD-BLE-SERVICES`

The Find stage must first open the browser's device chooser filtered to the knowledge base's known
services and name prefixes, with every known service UUID passed as an optional service. The scan
must start only from a tap by the person.

**Acceptance Criteria:**
1. Given an FTMS treadmill advertising `0x1826`, when the person taps "Find the device", then the
   chooser lists it and `requestDevice` was called with a filter including `0x1826` and with
   `optionalServices` holding every known service UUID that is not on Chrome's blocklist.
2. Given the agent decides to scan, when no tap by the person has happened, then no chooser opens and
   the agent is told the scan needs a tap.
3. Given the person cancels the chooser, when the cancel is reported, then Gattsby offers to scan
   again or to scan for all devices.

---

## FR-012: Widen to all devices when needed
**Traces to:** L1-004 · **Phase:** MVP · **Platform:** `PD-BLE`, `PD-BLE-SERVICES`

If the filtered scan finds nothing the person recognises, Gattsby must offer a scan that accepts all
devices, still passing every known service UUID as an optional service, and explain that names in
that list may be unfamiliar.

**Acceptance Criteria:**
1. Given the person cancelled a filtered scan and said the device was not listed, when Gattsby
   continues, then it offers "Show all nearby devices".
2. Given the person accepts, when the chooser opens, then `requestDevice` was called with
   `acceptAllDevices: true` and the full optional-service list.

---

## FR-013: Tell several candidates apart
**Traces to:** L1-004 · **Phase:** MVP (guided) / P2 (automatic) · **Platform:** `PD-ADV` (automatic only)

When the person cannot tell which listed device is theirs, Gattsby must run `power_cycle_match`
([TOOL-005](#tool-005-power_cycle_match)): ask the person to watch the list, turn the machine off,
note which entry disappears, turn it on and confirm it returns. Where advertisement watching is
available, Gattsby must do the matching itself.

**Acceptance Criteria:**
1. Given advertisement watching is not available, when the person says there are several candidates,
   then Gattsby guides them to turn the machine off, asks which entry disappeared, and records the
   answer as an observation.
2. Given advertisement watching is available and three candidates are being watched, when the
   machine is turned off and on, then Gattsby names the one candidate whose advertisements stopped
   and resumed.
3. Given the person closes Chrome's chooser and says several names look alike, when they supply the
   names, then the activity feed identifies those names as reported by the person. The person can
   continue to the guided match without supplying names.

---

## FR-014: Handle a device that cannot be found
**Traces to:** L1-004 · **Phase:** MVP

If no scan finds the device, Gattsby must check the usual causes in order (device off or asleep,
another app connected, out of range), and, if they are ruled out, conclude by elimination that the
device may use Bluetooth Classic, ANT+, Wi-Fi or USB, and issue the verdict *Not connectable* with
the reasons.

**Acceptance Criteria:**
1. Given two scans found nothing the person recognised, when Gattsby continues, then it asks, in
   order, whether the console is on and awake, whether any other app or watch is connected, and asks
   the person to stand within 2 metres.
2. Given all three are confirmed and a third scan finds nothing, when Gattsby concludes, then the
   verdict is *Not connectable*, with the evidence that Bluetooth Low Energy was not found and the
   note that the device may use Bluetooth Classic, ANT+, Wi-Fi or USB.

---

### Connection

## FR-015: Connect to the chosen device
**Traces to:** L1-005 · **Phase:** MVP · **Platform:** `PD-BLE`

Gattsby must connect to the GATT server of the device the person chose, show the device's name and
the connection state, and record the connection time.

**Acceptance Criteria:**
1. Given the person chose a device in the chooser, when Gattsby connects, then the screen shows the
   device's name and "Connected" within 10 seconds, or a failure with its reason.
2. Given the device's name contains markup such as `<b>`, when it is shown, then it is shown
   literally as text.

---

## FR-016: Recover from a dropped connection
**Traces to:** L1-005 · **Phase:** MVP · **Platform:** `PD-BLE`

On an unexpected disconnect Gattsby must pause the agent loop, record the drop in the raw log, try to
reconnect up to 3 times with growing delays (1, 2 and 4 seconds), restore notification
subscriptions, and resume. If every attempt fails it must ask the person to check the device and
offer to retry or stop.

**Acceptance Criteria:**
1. Given a connected device that drops, when the drop is reported, then the agent loop pauses, the
   drop is in the raw log with its timestamp, and a reconnect is attempted after 1 second.
2. Given the reconnect succeeds, when it completes, then every earlier notification subscription is
   active again and the loop resumes from the interrupted step.
3. Given three reconnects fail, when the third fails, then the person is asked to check the device,
   with "Try again" and "Stop".
4. Given a drop, when the investigation is later exported, then no step or recording before the drop
   is missing or corrupted.

---

## FR-017: Detect a device held by another central
**Traces to:** L1-005 · **Phase:** MVP · **Platform:** `PD-BLE`

When a connection is refused, drops within 5 seconds of connecting twice, or the device is not seen
although the person says it is on, Gattsby must suspect another connection and ask the person to
disconnect the console's app, watches and phones, and to power-cycle the device if that does not
help.

**Acceptance Criteria:**
1. Given a device that disconnects within 5 seconds of connecting on two attempts, when the second
   drop happens, then Gattsby asks the person to disconnect other apps and watches and records the
   suspicion as an observation.
2. Given the person has done so, when they tap "Done", then Gattsby reconnects.

---

## FR-018: Release the connection
**Traces to:** L1-005 · **Phase:** MVP · **Platform:** `PD-BLE`

Gattsby must stop notifications and disconnect when the investigation finishes or is stopped, when
the person leaves the investigation screen, and when the page is hidden for more than 60 seconds
with no recording running.

**Acceptance Criteria:**
1. Given a verdict was issued, when the verdict screen appears, then the device is disconnected and no
   notification listener remains.
2. Given the person navigates to the history during an investigation, when they confirm, then the
   device is disconnected.

---

### Identification

## FR-019: Enumerate and record the GATT layout
**Traces to:** L1-006 · **Phase:** MVP · **Platform:** `PD-BLE-SERVICES`

Once connected, Gattsby must list every reachable primary service and its characteristics with their
properties, name the known ones from the knowledge base, and record the layout in the investigation.

**Acceptance Criteria:**
1. Given a connected FTMS treadmill, when the GATT layout is enumerated, then the record lists
   `0x1826` with Treadmill Data (`0x2ACD`), Fitness Machine Feature (`0x2ACC`) and Fitness Machine
   Control Point (`0x2AD9`), each with its properties.
2. Given a device with a service not in the known-UUID list, when the layout is enumerated, then
   Gattsby records that some services may be invisible to the browser (see FR-023).

---

## FR-020: Read Device Information
**Traces to:** L1-006 · **Phase:** MVP

Where the Device Information Service (`0x180A`) is present, Gattsby must read the manufacturer name,
model number, serial number, hardware, firmware and software revisions that exist, and record each as
an observation.

**Acceptance Criteria:**
1. Given a device whose Device Information gives manufacturer "Acme" and model "T100", when it is
   read, then the hypothesis's maker and model are "Acme" and "T100", with the reads as evidence.
2. Given Device Information is absent, when Identify runs, then Gattsby continues without it and
   records its absence.

---

## FR-021: Match against known profiles before asking the model
**Traces to:** L1-006 · **Phase:** MVP

Gattsby must score the GATT layout, the device name and any manufacturer data against the knowledge
base with deterministic code, and must apply its heuristics (for example "FTMS present → decode FTMS
first") before the model is consulted. The model is consulted only when no candidate scores above
the heuristic threshold or two candidates are within 10 points of each other.

**Acceptance Criteria:**
1. Given a device exposing `0x1826` with Treadmill Data, when Identify runs, then the hypothesis
   becomes "FTMS treadmill" from the heuristics alone and the next step is the Standard path, with no
   model call made for that decision.
2. Given a device exposing only unknown services, when Identify runs, then the model (or, in
   checklist mode, the checklist) chooses the next step.

---

## FR-022: Read a photo of the model plate or console
**Traces to:** L1-006 · **Phase:** P2 · **Platform:** `PD-CAMERA`, `PD-PROMPT-IMAGE`

When the maker or model is still unknown after Device Information, Gattsby may ask the person for a
photo of the model plate or console and pass it to the on-device model to read the maker, model and
serial text. The text read is evidence with a confidence, never fact.

**Acceptance Criteria:**
1. Given full agent mode with image input available, when the person takes a photo of a model plate,
   then the text the model read is shown to the person to confirm or correct before it is recorded.
2. Given image input is not available, when the photo step would run, then Gattsby asks the person to
   type the model instead.

---

## FR-023: Report services the browser cannot see
**Traces to:** L1-006 · **Phase:** MVP · **Platform:** `PD-BLE-SERVICES`

Gattsby must state, in the investigation and in the profile, that services not in its known-UUID
list, and services on Chrome's blocklist, are invisible to the browser, and must raise a missing-tool
request when the evidence (advertised UUIDs not reachable, a brand with no known UUIDs) suggests
there are hidden services.

**Acceptance Criteria:**
1. Given a device advertising a 128-bit service UUID that is not in the knowledge base, when Identify
   runs, then a missing-tool request is raised naming the UUID, with the advertisement as evidence.
2. Given any verdict, when the profile is built, then it lists the services that were requested but
   not reachable.

---

### Standard protocol verification

## FR-024: Subscribe to and decode standard data
**Traces to:** L1-007 · **Phase:** MVP

When a standard service is present, Gattsby must subscribe to its data characteristic, decode it with
the knowledge base's decoder, and record the decoded fields with the raw bytes.

**Acceptance Criteria:**
1. Given an FTMS treadmill sending Treadmill Data, when Gattsby subscribes, then instantaneous speed,
   total distance and elapsed time (where the flags say they are present) are decoded with their
   units and stored next to each raw notification.
2. Given an FTMS bike sending Indoor Bike Data, when Gattsby subscribes, then speed, cadence,
   resistance level and power (where present) are decoded.
3. Given a payload whose flags announce more bytes than it holds, when it is decoded, then the decoder
   reports a decode error for that notification and does not crash.

---

## FR-025: Confirm decoded values with a physical action
**Traces to:** L1-007 · **Phase:** MVP

Gattsby must ask the person for a known action (walk faster, pedal harder, increase incline on the
console) and must confirm that the matching decoded metric moves the expected way within 15 seconds.
A metric counts as *confirmed* only when it does.

**Acceptance Criteria:**
1. Given an FTMS treadmill at a walking speed, when the person is asked to speed up on the console and
   decoded speed rises by at least 0.5 km/h within 15 seconds, then speed is marked *confirmed*.
2. Given decoded speed does not change, when 15 seconds pass, then speed is marked *not confirmed*,
   the person is asked whether the belt sped up, and the answer is recorded.
3. Given an FTMS treadmill, when speed and distance are confirmed, then the verdict can be
   "Connected — FTMS" (brief, MVP acceptance criterion 1).

---

## FR-026: Show live metrics
**Traces to:** L1-007 · **Phase:** MVP

While a device is subscribed, Gattsby must show each decoded metric with its unit, updated as
notifications arrive, readable at arm's length.

**Acceptance Criteria:**
1. Given a heart-rate strap, when it is subscribed, then live BPM is shown and updates within 1 second
   of each notification (brief, MVP acceptance criterion 2).
2. Given a viewport under 576 px wide, when live metrics are shown, then the metric being confirmed is
   at least 48 px tall.

---

## FR-027: Determine readable metrics and their decoding rules
**Traces to:** L1-007 · **Phase:** MVP

For each readable metric Gattsby must record, in the profile, the characteristic, the byte offset (or
the flag rule that sets it), the type, the scale, the unit, and whether it was confirmed by live data.
For FTMS it must read Fitness Machine Feature (`0x2ACC`) to know which metrics the device claims.

**Acceptance Criteria:**
1. Given an FTMS treadmill whose feature bits claim total distance and incline, when the profile is
   built, then both are listed as readable with their decoding rules, each marked *confirmed* or
   *claimed only*.
2. Given a metric claimed by the feature bits that never appears in the data, when the profile is
   built, then it is listed as *claimed, not seen*.

---

### Proprietary protocol analysis

## FR-028: Record a baseline and activity levels
**Traces to:** L1-008 · **Phase:** MVP

On the proprietary path Gattsby must subscribe to every characteristic that notifies or indicates,
record an idle baseline, then ask the person for two or three activity levels (for example slow,
medium, fast) and record each, with the level as a label.

**Acceptance Criteria:**
1. Given a device with only unknown services, when the proprietary path starts, then Gattsby records
   at least 10 seconds idle and 10 seconds at each of two levels, each labelled.
2. Given a characteristic sends nothing during any recording, when the recordings end, then it is
   recorded as *silent*.

---

## FR-029: Find the fields that vary
**Traces to:** L1-008 · **Phase:** MVP

Gattsby must compare the recordings and name the byte positions that change between labels and those
that change within a label (counters, noise), per characteristic and per packet length.

**Acceptance Criteria:**
1. Given a device whose byte 5 rises with effort, when the person changes effort, then byte 5 is
   reported as varying with the action, with the recordings as evidence (brief, MVP acceptance
   criterion 3).
2. Given at least one varying field and no confident decoding, when the investigation concludes, then
   the verdict is *Partially decoded* or *Needs a missing tool*, with the varying fields as evidence.

---

## FR-030: Correlate fields with actions and guess encodings
**Traces to:** L1-008 · **Phase:** P2

Gattsby must rank varying fields by correlation with the person's actions and test candidate
encodings (unsigned and signed 8, 16 and 32-bit, both byte orders, scales 1, 0.1, 0.01, 0.001)
against the expected range of the metric the person described.

**Acceptance Criteria:**
1. Given bytes 5–6 hold speed as little-endian uint16 in 0.01 km/h, when the person walks at 3, 5 and
   7 km/h, then the top-ranked candidate is "bytes 5–6, uint16 LE, ×0.01, km/h".
2. Given no candidate fits the expected range, when the guesser finishes, then it reports no fit
   rather than the closest wrong one.

---

## FR-031: Detect proprietary framing
**Traces to:** L1-008 · **Phase:** P2

Gattsby must look for constant headers, length bytes, sequence counters and checksums (sum, XOR, CRC-8,
CRC-16) in proprietary packets, and record any it finds as part of the decoding rule.

**Acceptance Criteria:**
1. Given packets starting `F0` with a length byte at offset 2 and a final byte equal to the 8-bit sum
   of the preceding bytes, when framing is detected, then the header, length and checksum are each
   reported with the share of packets that fit them.

---

## FR-032: Try a known vendor handshake when data is silent
**Traces to:** L1-008 · **Phase:** P2

When a device matches a vendor signature but sends no data, Gattsby may propose the vendor's known
initialisation sequence from the knowledge base. Sending it is a `write` and needs approval
(FR-034).

**Acceptance Criteria:**
1. Given a device matching a vendor signature with a known handshake and every characteristic silent,
   when the agent proposes the handshake, then the person sees what it is for and its bytes, and
   nothing is written until they approve.
2. Given the handshake was sent and data starts, when the investigation concludes, then the profile
   lists the handshake as required.

---

## FR-033: Never bypass encryption or authentication
**Traces to:** L1-008 · **Phase:** MVP

When a device requires pairing, bonding, encryption or an authentication exchange Gattsby does not
know, Gattsby must record the evidence, raise a missing-tool request and stop that line of
investigation. It must never try to guess keys, replay captured authentication or force pairing.

**Acceptance Criteria:**
1. Given a characteristic read fails with an insufficient-authentication or encryption error, when the
   error is reported, then a missing-tool request is raised with the error as evidence, and no other
   attempt is made on that characteristic.
2. Given any investigation, when its raw log is inspected, then it holds no write that was not either
   a known command or handshake from the knowledge base, approved by the person.

### Safe device control

## FR-034: Ask for approval for every write and control call
**Traces to:** L1-009 · **Phase:** MVP

Before any tool of safety class `write` or `control` runs, Gattsby must show the person what will be
sent, to which characteristic, what it is expected to do, and its risk, and must run it only after
the person taps "Send". The approval covers that one call. No mode, setting, earlier approval or
model output may skip it. `emergency_stop` is the one exception: it runs on the person's own tap,
which is its approval.

**Acceptance Criteria:**
1. Given the agent proposes `request_control`, when the approval prompt is shown, then nothing has been
   written to the device.
2. Given the person taps "Don't send", when the decision is recorded, then nothing is written, the tool
   returns `APPROVAL_DENIED` to the agent, and the agent may not propose the same call again in the
   next 3 steps.
3. Given the person approved one `send_command`, when the agent proposes a second, then a new approval
   prompt is shown (brief, MVP acceptance criterion 5).
4. Given a fake `navigator.bluetooth`, when any behaviour spec runs, then every recorded write is
   preceded by a recorded approval for that call.

---

## FR-035: Remind the person before any motion command
**Traces to:** L1-009 · **Phase:** MVP

Before a command that can make the device move or change its load (start, set speed, set incline,
set resistance, set power target), the approval prompt must tell the person to stand clear and to
know where the machine's own physical stop is, and must ask them to confirm that they do.

**Acceptance Criteria:**
1. Given the agent proposes "start" to a treadmill, when the approval prompt is shown, then it tells
   the person to stand clear of the belt and to locate the emergency stop key or button, and "Send"
   is disabled until they tick "I am clear and know where the stop is".
2. Given the agent proposes "stop", when the approval prompt is shown, then no stand-clear
   confirmation is required.

---

## FR-036: Keep every command conservative
**Traces to:** L1-009 · **Phase:** MVP

Gattsby must take command values only from the knowledge base's safe limits for the device's type,
must start with the lowest-risk command, must change one value by the smallest step, and must refuse
any value above the limits, whatever the model proposes.

**Acceptance Criteria:**
1. Given the safe limit for a first treadmill speed is 2.0 km/h, when the agent proposes 8.0 km/h, then
   the action is refused with `UNSAFE_VALUE` and no approval prompt is shown.
2. Given the device's supported resistance range has an increment of 1, when the agent proposes a
   resistance change, then the only change offered is ±1 from the current level.
3. Given no safe limit exists for the device's type, when the agent proposes a motion command, then it
   is refused with `UNSAFE_VALUE` and a missing-tool request is raised.

---

## FR-037: Request control and report the result
**Traces to:** L1-009 · **Phase:** MVP

For FTMS, Gattsby must send Request Control (`0x00`) to the Fitness Machine Control Point, with
indications enabled, and must report the response's result code (success, op code not supported,
invalid parameter, operation failed, control not permitted) or a timeout after 5 seconds.

**Acceptance Criteria:**
1. Given an approved Request Control, when the device indicates `80 00 01`, then the result is
   "Success" and controllable features may be tested.
2. Given the device indicates `80 00 05`, when the result is reported, then it is "Control not
   permitted", recorded as a connection quirk, and no further control command is proposed.

---

## FR-038: Test one command and confirm its effect
**Traces to:** L1-009 · **Phase:** MVP

The Control stage is optional and must offer the person the choice to skip it. If they take it,
Gattsby must send one low-risk command, ask the person whether the machine did what was expected,
check the decoded data where it can, and then send stop (FTMS Stop or Pause, or the vendor's
equivalent), also with approval.

**Acceptance Criteria:**
1. Given a connected FTMS bike with control granted, when the person agrees to test control, then one
   resistance change of +1 is proposed, and after it is sent the person is asked "Did the resistance
   change?"
2. Given the person answers "Yes" and the decoded resistance level changed, when the result is
   recorded, then "set resistance" is listed as controllable and *confirmed* in the profile.
3. Given the command test finished, when Gattsby continues, then it proposes stop or a return to the
   starting value before concluding.
4. Given the person chooses to skip Control, when the investigation concludes, then controllable
   features are listed as *claimed only*, from the feature bits.
5. Given live data moves against the test command, when Gattsby detects it, then it blocks further
   test commands and shows the machine's physical stop instruction with Emergency stop in reach.

---

## FR-039: Offer an emergency stop at all times
**Traces to:** L1-009 · **Phase:** MVP

While a device is connected, an emergency stop must be visible on every screen, reachable in one tap,
and must: send the device's stop or reset command where one is known (FTMS Stop, then Reset); refuse
every later `write` or `control` call for the rest of the investigation; stop the agent loop; and
record the event. It must work even while an approval prompt or model call is pending.

**Acceptance Criteria:**
1. Given a treadmill moving after an approved start, when the person taps "Emergency stop", then FTMS
   Stop is written within 500 ms, the agent loop stops, and the screen says to use the machine's own
   stop if it is still moving.
2. Given emergency stop was used, when the agent or the checklist would run any `write` or `control`
   tool, then it is refused with `EMERGENCY_STOPPED`.
3. Given a model call is in progress, when the person taps "Emergency stop", then the call is aborted
   with its `AbortController`.
4. Given a device with no known stop command, when emergency stop is used, then Gattsby disconnects,
   stops the loop, and tells the person to use the machine's own stop.

---

## FR-040: Determine controllable features
**Traces to:** L1-009 · **Phase:** MVP

For each controllable feature (start, stop, target speed, incline, resistance, power target) Gattsby
must record in the profile how it is commanded (op code and parameter encoding, or vendor command
bytes), its supported range where the device reports one, and whether it was *confirmed*, *claimed
only* or *refused* by the device.

**Acceptance Criteria:**
1. Given an FTMS treadmill whose Target Setting Features claim speed and incline, when the profile is
   built, then "target speed" (op code `0x02`, uint16, 0.01 km/h) and "target incline" (op code
   `0x03`, sint16, 0.1 %) are listed with their supported ranges.

### Agent orchestration

## FR-041: Build a compact state for each decision
**Traces to:** L1-010 · **Phase:** MVP · **Platform:** `PD-PROMPT`

Before each model call the orchestrator must build a state holding only: the device facts so far,
the current hypothesis with its confidence, the last 5 tool results as one-line summaries, the
current playbook stage, and the tools allowed at that stage. Raw bytes are never sent to the model;
summaries are.

**Acceptance Criteria:**
1. Given 12 tool results so far, when the state is built, then it holds exactly the last 5 summaries.
2. Given any state, when it is measured, then it is within the prompt budget of NFR-020.
3. Given a recording of 500 notifications, when its result is summarised for the model, then the
   summary is one line of at most 200 characters.

---

## FR-042: Constrain the model to one JSON action
**Traces to:** L1-010 · **Phase:** MVP · **Platform:** `PD-PROMPT`

Each model call must request structured output with a JSON schema (`responseConstraint`) that allows
exactly one action: `call_tool` (tool name and input), `ask_user`, `update_hypothesis`,
`request_missing_tool` or `finish`. Gattsby must not depend on native tool calling.

**Acceptance Criteria:**
1. Given a model call, when it is made, then it carries a `responseConstraint` describing the five
   action shapes.
2. Given a model response, when it is parsed, then it is exactly one action or it is rejected.

---

## FR-043: Validate every action before running it
**Traces to:** L1-010 · **Phase:** MVP

The orchestrator must check each action against its schema, the named tool's input schema and
preconditions, the tools allowed at the current stage, and the safety rules, and must refuse any
action that fails, with a reason the model sees in the next state. Each refusal counts as a step.

**Acceptance Criteria:**
1. Given the model returns `call_tool` for a tool not in the registry, when it is validated, then it is
   refused with `UNKNOWN_TOOL` and nothing runs.
2. Given the model returns `send_command` before `request_control` succeeded, when it is validated,
   then it is refused with `PRECONDITION_FAILED`.
3. Given the model returns `call_tool` with an input missing a required field, when it is validated,
   then it is refused with `INVALID_INPUT`.

---

## FR-044: Summarise each result
**Traces to:** L1-010 · **Phase:** MVP

Every tool must return, besides its full output (stored in the investigation), a one-line summary of
at most 200 characters for the model's state and the person's activity feed.

**Acceptance Criteria:**
1. Given `enumerate_gatt` found 4 services, when it returns, then its summary names the services by
   their knowledge-base names and fits in 200 characters.

---

## FR-045: Always end the loop
**Traces to:** L1-010 · **Phase:** MVP

The loop must stop when: the model returns `finish`; the hypothesis confidence reaches the finish
threshold and the stage's checks are done; the step budget is reached; N consecutive steps add no new
observation; the person stops; or emergency stop is used. On every stop other than `finish`,
Gattsby must still build a verdict and profile from what is known. The threshold, budget and N are
configuration (assumed defaults: 0.9, 40 steps, 5 steps; see A-05).

**Acceptance Criteria:**
1. Given the model never returns `finish`, when 40 steps have run, then the loop stops and the verdict
   is built from the observations so far, with "step budget reached" recorded.
2. Given five consecutive steps added no observation, when the fifth ends, then the loop stops with "no
   progress" recorded.
3. Given the model repeats the same refused action, when it does so a third time, then it counts as no
   progress.

---

## FR-046: Run deterministic heuristics before the model
**Traces to:** L1-010 · **Phase:** MVP

At each stage the orchestrator must apply the playbook's deterministic rules first and consult the
model only when the rules leave more than one reasonable next step.

**Acceptance Criteria:**
1. Given an FTMS treadmill, when the whole investigation runs in full agent mode, then the model is
   consulted no more than 5 times (the rules decide every other step).
2. Given the same treadmill, when the investigation runs in checklist mode, then the same verdict is
   reached.

---

## FR-047: Time out and abort model calls
**Traces to:** L1-010 · **Phase:** MVP · **Platform:** `PD-PROMPT`

Each model call must have a timeout (assumed 10 seconds; see A-05) and an `AbortController`. A timed
out call is aborted and counts as a failed step. Stop and emergency stop abort a pending call at
once.

**Acceptance Criteria:**
1. Given a model call that has not answered after 10 seconds, when the timeout fires, then the call is
   aborted and the step is recorded as timed out.

---

## FR-048: Show what the agent is doing
**Traces to:** L1-010 · **Phase:** MVP

Gattsby must show the current playbook stage, the step that is running in plain language, and an
activity feed of the one-line summaries, so that the person always knows what is happening and why
they are being asked something. Model text is shown as text, never as HTML.

**Acceptance Criteria:**
1. Given the agent is reading Device Information, when the person looks at the screen, then the stage
   reads "Identify" and the step reads "Reading the maker and model".
2. Given a model output containing `<img src=x onerror=alert(1)>`, when it is shown, then it appears
   literally and no script runs.

## FR-049: Run the playbook as a checklist
**Traces to:** L1-002 · **Phase:** MVP

In checklist mode, Gattsby must run the same seven playbook stages with the same tools, branching on
deterministic rules and the person's answers instead of model actions, and must produce the same
kinds of verdict and profile.

**Acceptance Criteria:**
1. Given no model is available and an FTMS treadmill that is powered on, when the person follows the
   checklist, then Gattsby reports "Connected — FTMS" with speed and distance confirmed by live data
   (brief, MVP acceptance criterion 4).
2. Given checklist mode and a device with only unknown services, when the person follows the
   checklist, then the proprietary-path recordings run and the verdict is *Partially decoded* or
   *Needs a missing tool*.
3. Given the checklist offers a tool, when the person waits two minutes without making a choice,
   then Gattsby asks “Still there?”. Choosing Continue returns to the same options.

### Hypotheses, verdict and device profile

## FR-053: Track the hypothesis with evidence
**Traces to:** L1-012 · **Phase:** MVP

Gattsby must hold one current hypothesis (protocol, maker, model, device type, confidence from 0 to 1,
and evidence references) and keep every earlier version with the step that changed it.
Confidence is computed by deterministic scoring; the model may propose a hypothesis but not set its
confidence above what the scoring supports.

**Acceptance Criteria:**
1. Given three `update_hypothesis` actions, when the record is exported, then all three versions are
   present, each with its step number and evidence.
2. Given the model proposes confidence 0.95 with no supporting observation, when it is applied, then
   the stored confidence is the deterministic score instead.

---

## FR-054: Issue one verdict
**Traces to:** L1-012 · **Phase:** MVP

Every investigation must end with exactly one verdict from this set (wording provisional; OQ-06):

| Verdict | When |
|---|---|
| Connected — *protocol* (for example "Connected — FTMS") | A known protocol was identified and at least one metric confirmed by live data |
| Partially decoded | Some fields were decoded or found varying, but not enough for a known protocol |
| Needs a missing tool | Progress was blocked by a capability Gattsby lacks |
| Not connectable | No Bluetooth Low Energy device was found or reachable |
| Stopped by the person | The person stopped before a verdict |

**Acceptance Criteria:**
1. Given an FTMS treadmill with speed and distance confirmed, when the investigation concludes, then
   the verdict is "Connected — FTMS".
2. Given a heart-rate strap with BPM confirmed, when the investigation concludes, then the verdict is
   "Connected — Heart Rate" and live BPM was shown.
3. Given any investigation, when it ends, then it holds exactly one verdict.

## FR-055: Build the device profile
**Traces to:** L1-012 · **Phase:** MVP

The device profile must hold: profile format version, knowledge-base version, device name, maker,
model, firmware, advertised and discovered UUIDs, unreachable services, protocol and confidence,
readable metrics with decoding rules (characteristic, offset or flag rule, type, scale, unit,
confirmation), controllable features with command bytes and ranges, required handshake, connection
quirks, verdict, evidence references, date, and the optional location label. It must not hold the
raw log; that stays in the investigation record.

**Acceptance Criteria:**
1. Given a finished FTMS investigation, when its profile is built, then it validates against the
   published profile JSON Schema.
2. Given a profile, when it is inspected, then every metric and feature has at least one evidence
   reference that resolves to an entry in its investigation record.

**Acceptance Criteria:**

   any origin but its own.

## 2. Non-functional requirements (NFR)

### Performance

## NFR-001: Time to verdict for an FTMS machine
**Traces to:** L1-019 · **Phase:** MVP

For an FTMS treadmill or bike that is powered on and free of other connections, the time from opening
the app to the verdict must be under 3 minutes, with the model already downloaded (full agent mode) or
in checklist mode, excluding the time the person takes to answer beyond 5 seconds per prompt.

**Acceptance Criteria:**
1. Given the simulated FTMS treadmill and scripted answers given in 5 seconds each, when an
   investigation runs from app open to verdict, then it finishes in under 3 minutes.
2. Given a real FTMS treadmill in a hardware smoke test run by a person, when they follow the prompts,
   then the verdict appears in under 3 minutes.

---

## NFR-002: Agent step latency
**Traces to:** L1-019 · **Phase:** MVP · **Platform:** `PD-PROMPT`

Once the model is loaded, each model decision (state built, model answers, action validated) must take
under 3 seconds at the 90th percentile on a typical laptop (assumed: 4-core CPU, 16 GB RAM, integrated
GPU, meeting Chrome's model requirements; see A-07). Deterministic steps must take under 200 ms,
excluding Bluetooth and the person.

**Acceptance Criteria:**
1. Given the reference laptop with the model loaded, when 20 decisions are timed during an FTMS
   investigation, then the 90th percentile is under 3 seconds.
2. Given the orchestrator with a fake model that answers at once, when 100 deterministic steps are
   timed, then each takes under 200 ms.

---

## NFR-003: Keep up with notifications
**Traces to:** L1-019 · **Phase:** MVP

The BLE layer and the recorder must log and decode notifications at up to 50 per second per
characteristic, across up to 4 characteristics at once, without dropping one or delaying the UI by
more than one frame.

**Acceptance Criteria:**
1. Given a fake device sending 50 notifications per second on 4 characteristics for 60 seconds, when
   they are recorded, then all 12,000 are logged in order with timestamps.

---

## NFR-004: Small initial load
**Traces to:** L1-019 · **Phase:** MVP

The initial bundle (what loads before the home screen is interactive) must be at most 250 KB
compressed (assumed budget; see A-08), and the home screen must be interactive within 2 seconds on a
mid-range phone over a fast 4G connection. The model adapter, analysis tools and camera code are
loaded on demand.

**Acceptance Criteria:**
1. Given a production build, when the bundle budget check runs, then the initial bundle is within 250 KB
   compressed, and the build fails otherwise.

---

## NFR-005: Bounded memory
**Traces to:** L1-019 · **Phase:** MVP

Memory held during an investigation must be bounded: the model's history is capped (FR-041), raw
traffic is written to IndexedDB and kept in memory only in a window of the last 2,000 entries, and a
recording longer than 120 seconds is refused. Leaving the investigation screen releases its memory.

**Acceptance Criteria:**
1. Given a 30-minute investigation with continuous notifications at 20 per second, when the JS heap is
   sampled every minute, then it does not grow by more than 20 MB from minute 5 to minute 30.

---

### Reliability and offline operation

## NFR-006: Work offline after first load
**Traces to:** L1-020 · **Phase:** MVP · **Platform:** `PD-PWA`, `PD-PROMPT`

Gattsby must be an installable progressive web app whose service worker caches every static file, so
that, after one load online, it opens and runs a full investigation with no network. The model, once
downloaded, is cached by Chrome.

**Acceptance Criteria:**
1. Given Gattsby was loaded once online, when the network is off and the person opens it, then it loads
   and an investigation of the simulated FTMS treadmill reaches a verdict.

## NFR-007: Survive connection drops without corruption
**Traces to:** L1-020 · **Phase:** MVP

No connection drop, tab close, crash or model failure may leave an investigation unreadable or
inconsistent: each step is committed atomically (FR-060), and a partly written step is detectable and
discarded on reopening.

**Acceptance Criteria:**
1. Given 50 investigations each interrupted at a random step by a simulated drop or a page reload, when
   each is reopened, then every one opens, validates against the record schema, and can be resumed or
   concluded.

---

## NFR-008: Handle storage limits
**Traces to:** L1-020 · **Phase:** MVP · **Platform:** `PD-STORAGE`

Gattsby must request persistent storage on the first investigation, show storage use in the history,
and, when a write fails for lack of quota, stop recording, keep what is stored, and tell the person to
export and delete old investigations.

**Acceptance Criteria:**
1. Given a write that fails with a quota error, when it is reported, then recording stops, the
   investigation is still readable, and the person is told how to free space.

### Usability, accessibility and responsive layout

## NFR-009: Usable one-handed at arm's length
**Traces to:** L1-021 · **Phase:** MVP

live metric values at least 32 px on viewports under 768 px wide; touch targets at least 48 × 48 px
with at least 8 px between them; the primary action within the bottom third of the screen on

**Acceptance Criteria:**
1. Given a 390 × 844 viewport, when any prompt is shown, then its text is at least 20 px, its answers

## NFR-010: Responsive across all viewports
**Traces to:** L1-021 · **Phase:** MVP

Every screen must work at extra small (<576 px), small (≥576 px), medium (≥768 px), large (≥992 px) and

**Acceptance Criteria:**

3. Given a width of 992 px or more, when an investigation is running, then the prompt and the activity

### Privacy and security

## NFR-012: No data leaves the device
**Traces to:** L1-018 · **Phase:** MVP

At run time Gattsby must make no network request except for its own static files from its own origin.
There must be no analytics, telemetry, error reporting service, CDN, web font service or remote model
call. The Content Security Policy's `connect-src` must be `'self'`.

**Acceptance Criteria:**
1. Given every behaviour spec, when it runs, then any request to an origin other than the app's fails
   the spec.
2. Given the deployed app, when its headers are inspected, then `connect-src` is `'self'` and no
   third-party origin appears in any directive.

---

## NFR-013: Treat model output and device data as untrusted
**Traces to:** L1-018 · **Phase:** MVP

Model output, device names, characteristic values, answers, imported files and text read from photos
must be rendered as text, never as HTML, and never evaluated. The app must enforce Trusted Types
(`require-trusted-types-for 'script'`) and contain no `innerHTML`, `eval` or `new Function` on such
data.

**Acceptance Criteria:**
1. Given a fake device named `<img src=x onerror=alert(1)>` and a fake model whose output contains a
   `<script>` tag, when an investigation runs and is exported and re-imported, then no script runs and
   the text is shown literally everywhere.
2. Given the production build, when it is served with its Content Security Policy, then no Trusted
   Types violation is reported during the behaviour specs.

---

## NFR-014: Secure hosting
**Traces to:** L1-018 · **Phase:** MVP

Gattsby must be served only over HTTPS with HSTS, a strict Content Security Policy (`default-src
'self'`, no `unsafe-inline` or `unsafe-eval` for scripts, `object-src 'none'`, `frame-ancestors
'none'`), `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and a
`Permissions-Policy` allowing only `bluetooth`, `camera` (self) and nothing else.

**Acceptance Criteria:**
1. Given the deployed app, when its response headers are checked, then each header above is present
   with the stated value.

---

## NFR-015: Validate every import
**Traces to:** L1-018 · **Phase:** MVP

An imported file must be at most 20 MB, valid JSON, valid against the schema of its declared type and
version, and free of prototype-polluting keys (`__proto__`, `constructor`, `prototype`) before anything
is stored. Strings are length-limited by the schema.

**Acceptance Criteria:**
1. Given a 25 MB file, when it is imported, then it is refused before it is parsed.
2. Given a JSON file holding a `__proto__` key, when it is imported, then it is refused and
   `Object.prototype` is unchanged.

---

## NFR-016: Ask only for the permissions needed, when needed
**Traces to:** L1-018 · **Phase:** MVP

Gattsby must ask for Bluetooth only when the person taps to scan, for the camera only when the person
chooses to take a photo, and for persistent storage only when the first investigation starts. It must
never ask for location, notifications, microphone or contacts.

**Acceptance Criteria:**
1. Given a first visit, when the home screen loads, then no permission prompt is shown.

**Traces to:** L1-018 · **Phase:** P2 · **Platform:** `PD-CAMERA`, `PD-PROMPT-IMAGE`

Photos must be stored only in IndexedDB, passed only to the on-device model, stripped of EXIF metadata

### Safety

## NFR-018: No unapproved write is possible
**Traces to:** L1-017 · **Phase:** MVP

The only path from the agent or the checklist to a Bluetooth write must pass through the approval gate

## 3. Tool specifications (TOOL)

### Common rules for every tool

- Every tool is registered as FR-070 describes and returns the result envelope of FR-072:
  `{ ok, summary, data, error: { code, message }, evidence: [ids] }`.
- Inputs are validated against the tool's input schema before it runs (FR-043). Outputs are validated
  against its output schema before they are stored.
- `write` and `control` tools run only after an approval for that exact call (FR-034, NFR-018), and
  never after emergency stop (FR-039).
- A tool that opens the browser's device chooser cannot run without a user gesture. When the agent or
  the checklist calls one, the orchestrator shows a button ("Find the device") and the tool runs on
  the person's tap; if there is no tap within 2 minutes the tool returns `TIMEOUT`.
- Tools that touch the device need the BLE layer; tools in the Analysis group are pure functions of
  stored recordings and need no connection.

### Shared error codes

| Code | Meaning |
|---|---|
| `INVALID_INPUT` | The input failed the tool's input schema |
| `UNKNOWN_TOOL` | No tool of that name is registered |
| `NOT_ALLOWED_AT_STAGE` | The tool is not allowed at the current playbook stage |
| `PRECONDITION_FAILED` | A precondition is not met (for example, not connected) |
| `UNSUPPORTED` | A capability the tool needs is not available in this browser or platform |
| `BLE_UNAVAILABLE` | Bluetooth is off, absent or blocked by policy |
| `USER_CANCELLED` | The person cancelled the chooser, the camera or a prompt |
| `NOT_CONNECTED` | The device is not connected |
| `CONNECTION_FAILED` | A connection attempt failed |
| `TIMEOUT` | The operation did not finish in its time limit |
| `GATT_ERROR` | The device returned a GATT error (the ATT error code is in the message) |
| `SERVICE_NOT_PERMITTED` | The service was not in `optionalServices`, so the browser hides it |
| `BLOCKLISTED` | The UUID is on Chrome's GATT blocklist |
| `AUTH_REQUIRED` | The device needs authentication or encryption Gattsby does not have |
| `PROPERTY_MISSING` | The characteristic does not support the operation (read, notify, write) |
| `APPROVAL_REQUIRED` | A `write` or `control` call reached the BLE layer without a valid approval |
| `APPROVAL_DENIED` | The person declined the call |
| `UNSAFE_VALUE` | The value is outside the knowledge base's safe limits, or no safe limit exists |
| `EMERGENCY_STOPPED` | Emergency stop was used; no further write is allowed |
| `DEVICE_REJECTED` | The device answered a command with a non-success result code |
| `INSUFFICIENT_DATA` | The recordings are too short or too few for the analysis |
| `DECODE_ERROR` | The bytes do not fit the decoder |
| `STORAGE_FULL` | IndexedDB refused a write for lack of quota |
| `ABORTED` | The call was aborted by stop, emergency stop or a timeout |

## 6. Assumptions

These were needed to write testable requirements and are not stated in the brief. Each is to be
confirmed or corrected; changing one changes only the requirements that cite it.

| ID | Assumption | Cited by |
|---|---|---|
| A-01 | The *Gattsby: Behavior Description* was not supplied with the brief. Every user-facing string, screen and verdict wording here is provisional until it is added. | FR-054, all UI wording |
| A-02 | At MVP, full agent mode runs on a laptop and the phone runs checklist mode (pending OQ-01). | FR-005, FR-049, NFR-026 |
| A-03 | One investigation identifies one device. | FR-007, FR-055 |
| A-04 | Gattsby is hosted as static files on any HTTPS host that can set the response headers in NFR-014. | NFR-014 |
| A-05 | Agent loop defaults: finish confidence 0.9, step budget 40, no-progress stop after 5 steps, model call timeout 10 seconds, last 5 summaries in the state. All are configuration. | FR-041, FR-045, FR-047 |
| A-06 | The MVP test offers one downward treadmill increment of at most 0.1 km/h while moving, with a target at or below 6 km/h. It offers one upward bike resistance increment of at most one level, with a target at or below level 10. Both require the advertised range and a recent live reading. | FR-036, TOOL-022 |
| A-07 | "A typical laptop" means a 4-core CPU, 16 GB RAM and an integrated GPU that meets Chrome's requirements for Gemini Nano. | NFR-002 |
| A-08 | The initial bundle budget is 250 KB compressed. | NFR-004 |
| A-09 | Recordings last 10 seconds per level by default and at most 120 seconds. | FR-028, TOOL-013 |
| A-10 | The browser's chooser is drawn by Chrome and cannot be read by the page, so guided power-cycle matching relies on the person watching it. | FR-013, TOOL-005 |
| A-11 | Vendor facts come from public sources (vendor documentation, published open-source projects, the person's own recordings of their own devices), each cited. Gattsby does not reverse-engineer encryption. | FR-068 |
| A-12 | A standard metric is *confirmed* when it moves the expected way within 15 seconds of the person's action (speed by at least 0.5 km/h; distance increases while the belt moves). | FR-025 |
| A-13 | The Prompt API's shape is as Chrome documented it on 25 November 2026: `LanguageModel.availability()`, `LanguageModel.create()` with a download-progress monitor, `prompt()` with `responseConstraint` and an `AbortSignal`, and a reported context window. | FR-004, FR-042, FR-047, NFR-020 |
| A-14 | English is the only language at MVP. | All UI wording |
| A-15 | The Echelon known-UUID entry can be researched and sourced before the MVP ships. | FR-068 |
